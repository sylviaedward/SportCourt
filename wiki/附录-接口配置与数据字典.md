## 1. 调用方式与响应

页面请求 `http://127.0.0.1:8080/api/路径`，直接 Java 请求 `http://127.0.0.1:8081/路径`。下表只写 Java 路径，不加 `/api`。不要把 URL 上的大括号原样发给服务，它表示要替换的参数。

```json
{"success":true,"data":{"示例字段":"示例值"}}
```

业务失败通常形如：

```json
{"success":false,"errorMsg":"失败原因"}
```

响应空值字段会被 Jackson 省略，所以不一定同时出现所有四个字段。拦截器拒绝通常伴随 401/403/429；输入转换或异常处理的 HTTP 状态以实际响应为准，客户端同时检查 HTTP 与 success。

## 2. 实操一：不登录，先确认公开查询和缓存观察

下面命令从项目根目录执行。`sportcourt_api` 表示直接访问 Java；改成 `http://127.0.0.1:8080/api` 就是经 Nginx，后续路径保持一致。没有安装 curl 时也可以在浏览器开发者工具 Network 中看同样的响应。

```bash
sportcourt_api='http://127.0.0.1:8081'
curl -i "$sportcourt_api/actuator/health"
curl -i "$sportcourt_api/venue-type/list"
curl -i "$sportcourt_api/venue/catalog?page=1&size=12&sort=score"
```

先从 catalog 响应挑选真实存在的场馆，不假设所有环境的 ID 都相同。输入它的整数 ID：

```bash
read -r sportcourt_venue_id
curl -i "$sportcourt_api/venue/$sportcourt_venue_id"
curl -i "$sportcourt_api/experience/capabilities"
curl -i "$sportcourt_api/experience/cache?venueId=$sportcourt_venue_id"
```

第一条详情读会走正常浏览采集；cache 体验接口调用纯详情读取，用同一个请求连续读两次，避免观察缓存时额外生成浏览。成功响应中 `reads` 应有两个元素，每项都有 sequence、durationMicros 和 events。第二次读取通常能看到请求内缓存命中。

没有开启 experience 时，能力接口会给 enabled=false，体验操作返回未启用；这不是 venue ID 错误。缓存已经预热时首次 trace 没有 MySQL 很正常。查询耗时中的 `durationMicros` 是微秒，不要直接拿它与整次 curl 的网络耗时比较。

## 3. 实操二：正常登录后调用本人接口

<a id="section-03-01"></a>

### 发送验证码与取得 token

先输入自己的演示手机号，只输入合法数字，不把提示语当作值：

```bash
read -r sportcourt_phone
curl -i -X POST --get --data-urlencode "phone=$sportcourt_phone" "$sportcourt_api/user/code"
```

当前项目没有真实短信通道。查本次 Java 调试日志中的验证码，也可通过网页登录流程操作：

```bash
docker compose -p sport-court -f dev/docker-compose.yml logs --tail=100 java
```

输入本次六位验证码，然后登录：

```bash
read -r sportcourt_code
curl -i -X POST "$sportcourt_api/user/login" \
  -H 'Content-Type: application/json' \
  --data "{\"phone\":\"$sportcourt_phone\",\"code\":\"$sportcourt_code\"}"
```

确认 success=true，把 data 中的 token 内容复制出来，不含 JSON 引号，输入下一条 read：

```bash
read -r sportcourt_token
curl -i "$sportcourt_api/user/me" -H "authorization: $sportcourt_token"
```

业务认证头传原始 token，不加 `Bearer `。专用监控凭证才用 Bearer，不能混用。`user/me` 返回的 id 是用户 ID，用于核对身份，不是券或订单 ID。

验证码正确登录后会被消费，不能无限用同一验证码重复登录；再次登录按限流窗口重新发送。curl 不会自动使用浏览器 sessionStorage 的 token，浏览器也不会自动知道终端中保存的变量，两种客户端要分别提供认证头。

<a id="section-03-02"></a>

### 签到和连续天数

```bash
curl -i -X POST "$sportcourt_api/user/sign" -H "authorization: $sportcourt_token"
curl -i "$sportcourt_api/user/sign/count" -H "authorization: $sportcourt_token"
```

当天重复签到设置的是同一个 bit，连续天数不会因重复点击直接加一。具体按月位序和右移演算见 [04 章](04-登录权限与签到.md)。本例确实会签到，是本人业务操作；不把它归为纯查询。

## 4. 实操三：从真实券到本人订单，再到任务进度

先读取选中场馆的券列表：

```bash
curl -i "$sportcourt_api/bookingPass/list/$sportcourt_venue_id"
```

从响应中选择一张有效普通券，输入券 ID。若没有普通券，先用页面查看其他场馆；创建券属于管理动作，不能把任意 ID 当作可领商品。

```bash
read -r sportcourt_booking_pass_id
curl -i -X POST "$sportcourt_api/bookingPass-order/ordinary/$sportcourt_booking_pass_id" \
  -H "authorization: $sportcourt_token"
```

成功后的 data 是订单 ID。完整复制为十进制文本，输入变量，不用 JavaScript Number 转换长整型：

```bash
read -r sportcourt_order_id
curl -i "$sportcourt_api/bookingPass-order/$sportcourt_order_id" -H "authorization: $sportcourt_token"
curl -i "$sportcourt_api/bookingPass-order/mine?page=1" -H "authorization: $sportcourt_token"
curl -i "$sportcourt_api/experience/orders/$sportcourt_order_id" -H "authorization: $sportcourt_token"
```

检查普通领订场券返回的 ID、详情中的 ID、本人列表中的 ID 是否一致。重复领取同一张仍有效的普通券时返回原订单，不是每次新增一张。任务进度里没有立刻显示消费完成，可能只是异步传播尚未完成，刷新 GET 查询即可。

付费券通常是未付款 status=1；免费券可以直接 status=2。不能为了让页面显示成功就跳过模拟付款开关，或把 status=2 当作真实资金到账。

整点抢黄金时段时把领取路径换为 `/bookingPass-order/goldenSlot/券ID`，返回的订单号还要查 `/bookingPass-order/requests/订单ID`，成功受理与请求 SUCCESS 不相同。不要用普通订单的同步返回解释整点抢黄金时段。请求状态与消息任务详见 [08 章](08-整点抢黄金时段Lua与RedisStream.md)。

## 5. 实操四：Kafka 回执必须查刚才提交的 eventId

先开启体验与分析功能，再提交一次浏览体验；有登录头时记录该登录用户，省略头时为匿名：

```bash
curl -i -X POST "$sportcourt_api/experience/visits?venueId=$sportcourt_venue_id" \
  -H "authorization: $sportcourt_token"
```

成功响应包含 `submitted=3` 和 eventIds 数组。把三个小写 UUID 按逗号连接成一行输入，保持原值，不另造三个新 UUID：

```bash
read -r sportcourt_event_ids
curl -i --get "$sportcourt_api/experience/visits" \
  --data-urlencode "eventIds=$sportcourt_event_ids"
curl -i "$sportcourt_api/venue/hot-ranking?windowMinutes=5&limit=10"
```

回执响应是数组，每项含 eventId 与 state。PENDING 表示当前未查到对应持久事实，PERSISTED 表示已查到；它不返回个人身份或完整消息。若尚未完成，间隔几秒重复 GET，不重复 POST 制造更多事件，并留意体验入口的共享限流。

所有回执都 PERSISTED 之后，再看选中场馆的 PV 与窗口。热榜有刷新延迟，且其他访客可能也在贡献浏览，所以共享环境不能仅凭总数差值证明这三个 ID 已消费。匹配 ID 的回执才是本轮明确证据。

## 7. 场馆、分类与热榜（11）

| 方法与路径 | 权限 | 输入与说明 |
| --- | --- | --- |
| GET `/venue/{id}` | 公开 | 场馆详情，多层缓存；正常详情会采集浏览行为 |
| GET `/venue/search` | 公开 | 组合搜索，参数见下表 |
| GET `/venue/catalog` | 公开 | 可选 keyword/typeId，page 默认 1，size 默认 12，sort 默认 score |
| GET `/venue/batch` | 公开 | query `ids=1,2`，最多 40 个正 ID，复核当前数据库详情 |
| GET `/venue/areas` | 公开 | 当前登记的商圈 |
| POST `/venue` | 管理 | JSON Venue，新场馆 |
| PUT `/venue` | 管理 | JSON Venue，必须有 id，更新并登记失效事件 |
| GET `/venue/of/type` | 公开 | typeId 必填，current 默认 1，可选成对 x/y |
| GET `/venue/of/name` | 公开 | 可选 name，current 默认 1 |
| GET `/venue-type/list` | 公开 | 分类列表 |
| GET `/venue/hot-ranking` | 公开、分析开关 | windowMinutes 默认 60，仅支持 5/60；limit 默认 10，范围 1～100 |

`/venue/search` 主要参数：

| 参数 | 规则 |
| --- | --- |
| typeId | 必填，正整数 |
| keyword / area | 可选，名称/商圈或地址筛选 |
| maxPrice | 非负整数，元 |
| minScore | 0～50，45 表示 4.5 分 |
| hasBookingPass | true 时仅筛当前有可用券的场馆 |
| x / y | 同时提供，经度 [-180,180]、纬度 [-90,90]；须为有限数 |
| page / size | 默认 1/10；page 1～100000，size 1～20 |
| sort | score、price、distance；distance 必须有坐标 |

catalog 的 page 1～10000，size 1～20，keyword 长度最多 50，sort 仅 score/price；它与严格组合 search 不是完全相同的接口。

| GET `/actuator/prometheus` | 管理或专用监控凭证 | 指标，监控方式用 Bearer token |

运维是恢复手段，不是普通访客的演示按钮。先用 GET 查看，再确定是否有必要 POST；操作会审计，审计不保存完整请求体或认证 token。

## 13. Redis Key 与恢复来源

| Key / 模式 | 类型与意义 | 持久事实与边界 |
| --- | --- | --- |
| `login:code:{phone}` | String，一次性验证码 | Redis，2 分钟 |
| `login:token:{token}` | Hash，简要登录用户 | 实际前缀 login:token:，25 天滑动过期 |
| `cache:venue:{id}` | String JSON/空结果 | 可从 MySQL 重建，普通回源基础 30 分钟、CDC 重建 20 分钟，均加抖动 |
| `cache:booking_pass-list:{venueId}` | String 目录快照 | MySQL，基础 10 分钟加抖动 |
| `cache:booking_pass-meta:{id}` | String 券元数据 | MySQL，基础 10 分钟加抖动 |
| `{缓存Key}:version` | String，回填版本 | 失效栅栏，不能把旧回填当新值 |
| `lock:cache:{缓存Key}` | String，owner 租约 | 临时锁，不是业务事实 |
| `lock:order:ordinary:{userId}` | Redisson 锁结构 | 普通券竞争协调，不代替数据库 |
| `goldenSlot:stock:{booking_passId}` | String，入口可预占库存 | 恢复需数据库与在途预约，不能简单覆盖 |
| `goldenSlot:order:{booking_passId}` | Set，已占资格用户 | 实际前缀 goldenSlot:order:，补偿需核对对应订单身份 |
| `goldenSlot:activity:{booking_passId}` | Hash，活动时间/入口状态 | 与发布标记和恢复联动 |
| `goldenSlot:requests:{booking_passId}` | Hash，用户 → 订单映射 | 防重复与身份补偿 |
| `goldenSlot:request:{orderId}` | Hash，请求状态 | 临时约 7 天，登记后数据库预约优先 |
| `stream.orders` | Stream，入口待交接消息 | 消费组 g1，ACK 前保留恢复责任 |
| `post:liked:{postId}` | ZSet，点赞时间投影 | 新点赞事实在 tb_post_like |
| `follows:{userId}` | Set，关注投影 | 事实在 tb_follow_edge |
| `feed:{userId}` | ZSet，关注动态收件箱 | 约 1000 条；没有完整自动历史重建入口 |
| `venue:geo:{typeId}` | GEO，类别地点索引 | 场馆坐标在 MySQL；缺失时有查询回退 |
| `sign:{userId}:yyyyMM` | Bitmap，每月签到 | 当前只在 Redis，不跨月连续计算 |

## 15. 三套状态不要混淆

| 对象 | 状态 | 含义 |
| --- | --- | --- |
| 整点抢黄金时段预约 | PROCESSING / SUCCESS / REVIEW / FAILED | 是否正在履约、落库、待复核或明确失败 |

## 16. 只读 Redis 实验：观察形态，不手动改业务状态

初学者可先在隔离环境对临时教学 Key 练习 SETBIT、GEOADD、XADD；对应章节已经给出独立例子。下面则观察真实项目 Key，命令不会修改库存或确认消息。

```bash
# 查看选中场馆缓存是否存在、剩余寿命与版本
docker compose -p sport-court -f dev/docker-compose.yml exec -T redis \
  redis-cli TYPE "cache:venue:$sportcourt_venue_id"
docker compose -p sport-court -f dev/docker-compose.yml exec -T redis \
  redis-cli PTTL "cache:venue:$sportcourt_venue_id"
docker compose -p sport-court -f dev/docker-compose.yml exec -T redis \
  redis-cli GET "cache:venue:$sportcourt_venue_id:version"
# 整点抢黄金时段例子需要先选择真实整点抢黄金时段券，不能把普通券 ID 当作活动
docker compose -p sport-court -f dev/docker-compose.yml exec -T redis \
  redis-cli GET "goldenSlot:stock:$sportcourt_booking_pass_id"
docker compose -p sport-court -f dev/docker-compose.yml exec -T redis \
  redis-cli XINFO GROUPS stream.orders
docker compose -p sport-court -f dev/docker-compose.yml exec -T redis \
  redis-cli XPENDING stream.orders g1
```

PTTL 单位是毫秒，-2 表示不存在，-1 表示没有过期时间。没有缓存数据可能是失效后尚未重建；版本 Key 没过期不代表场馆数据永久不过期。不存在 Stream 或消费组时命令可能报错，应先确认业务是否初始化，而不是随意在共享环境重新建组。

XINFO 的 lag 与 XPENDING 回答不同问题：前者帮助观察还没读到的消息，后者观察已读但尚未确认的消息。pending=0 不能证明所有正式订单都已完成，任务可能已交接到数据库。不要为了“清零”而执行 XACK 或删除 Stream，确认动作必须跟随实际交接结果。

本章示例没有输出 token Hash 或验证码内容；查看业务身份使用 `user/me` 即可，不需要把 Redis 全部登录记录导出来。

## 17. SQL 实验：用一组 ID 找到事实、任务和回执

本节是数据库客户端中的排查查询，**不是在 Java 业务里引入 JDBC**。应用数据库访问继续用现有 Mapper → Service → Controller。先连接自己的数据库，执行 `SELECT DATABASE()` 核对实例和库名；不要在未知连接上复制修改语句。

<a id="section-17-01"></a>

### 一条普通订单关联哪些表

下面 SET 只定义 SQL 会话变量，不改表。将 0 替换为本轮订单号；0 是占位，原样执行不会拿到真实订单。

```sql
SELECT DATABASE();
SET @sportcourt_order_id = 0;

SELECT id, user_id, booking_pass_id, status, pay_value_snapshot,
       venue_id_snapshot, expire_at
FROM tb_booking_pass_order
WHERE id = @sportcourt_order_id;

SELECT id, kind, aggregate_id, state, attempts, consume_attempts,
       deliver_at, sent_at, consumed_at, lease_until, last_error
FROM tb_business_outbox
WHERE aggregate_id = @sportcourt_order_id
  AND kind IN ('ORDER_CREATED','ORDER_PAID','ORDER_CLOSED','ORDER_EXPIRE','GOLDEN_SLOT_FULFILL')
ORDER BY id;

SELECT consumer_group, event_id, processed_at
FROM tb_message_inbox
WHERE event_id IN (
  SELECT id FROM tb_business_outbox
  WHERE aggregate_id = @sportcourt_order_id
    AND kind IN ('ORDER_CREATED','ORDER_PAID','ORDER_CLOSED','ORDER_EXPIRE','GOLDEN_SLOT_FULFILL')
);
```

`aggregate_id` 不是所有 kind 共用的“订单外键”：在社区事件里也可能是约球动态或其他对象 ID，所以查询必须同时限定 kind。Outbox.id 才是可靠业务事件 ID，与订单号不同；Inbox 的 event_id 对应该事件 ID。

任务投递中可能出现 SENT 而没有 Inbox，稍后消费成功才出现 Inbox 与 DONE；ORDER_EXPIRE 在未到期限时等待并不代表失败。上面的字段能帮助解释这种中间状态。

<a id="section-17-02"></a>

### 整点抢黄金时段要额外看持久预约

```sql
SELECT order_id, booking_pass_id, user_id, state, attempts, reason,
       created_at, updated_at
FROM tb_golden_slot_reservation
WHERE order_id = @sportcourt_order_id;
```

预约不存在而 Redis 有预占，优先排查 Stream 尚未登记或交接失败；预约 PROCESSING 且有履约 Outbox，排查发送消费；预约 SUCCESS 则核对正式订单。这里只解释观察方向，不根据“查不到一行”就自动释放库存。

<a id="section-17-03"></a>

### 浏览事件与分钟桶

把示意字符串换为本次返回的一个 eventId，把 venue ID 换为本轮场馆：

```sql
SET @sportcourt_event_id = '替换成本次实际UUID';
SET @sportcourt_venue_id = 0;

SELECT event_id, venue_id, user_id, action, occurred_at_ms, bucket_ms
FROM tb_behavior_event
WHERE event_id = @sportcourt_event_id;

SELECT venue_id, bucket_ms, visits, orders, payments
FROM tb_venue_heat_bucket
WHERE venue_id = @sportcourt_venue_id
ORDER BY bucket_ms DESC LIMIT 10;
```

事件表是一条去重事实，桶表是多个事件汇总，不能拿它们的行数直接相等比较。`occurred_at_ms` 是事件时间，`bucket_ms` 是取整到分钟的毫秒值；它们不是 MySQL 的普通日期字符串。

UUID 型浏览 eventId、Outbox 数字事件 ID、orderId 是三种不同标识。分析订单事件还会使用由来源事件构成的稳定字符串 ID，查询前先明确来自哪个响应或表。

## 18. 为什么主键、唯一键和普通索引不能互相替代

| 约束或索引 | 约束什么 / 加速什么 | 不能代替什么 |
| --- | --- | --- |
| tb_ordinary_order_slot 联合主键 | 用户与券组合有稳定槽位，供行锁协调 | 不能自动完成订单状态校验 |
| tb_golden_slot_reservation 的资格唯一键 | 同活动当前有效资格避免重复占有 | 不能保证 Redis、消息、订单一起原子提交 |
| tb_business_outbox 的 idempotency_key 唯一键 | 指定业务交接重复执行不重复创建任务 | 不能保证只向 Broker 发送一次 |
| tb_message_inbox 联合主键 | 某消费组对某事件登记一次 | 不能替代不同副作用的幂等设计 |
| tb_behavior_event 主键 | 同 eventId 只登记一条事实 | 不能识别不同 eventId 其实是同一业务动作 |
| idx_follow_fanout | 按被关注作者与边 ID 分批查粉丝 | 不是独立的唯一身份约束 |
| idx_outbox_due / idx_outbox_lease | 缩小到期任务与超时租约的查询范围 | 不能决定任务是否已由另一个工作者完成 |

唯一键负责拒绝重复事实；普通索引负责更快定位；事务与业务条件负责把相关步骤串成正确状态变化。分布式锁则辅助协调竞争，它们分别解决不同层次的问题。

读迁移从 [V1](../src/main/resources/db/migration/V1__reliable_booking_pass_business.sql) 开始，再看后续版本添加的租约、消息、快照和分析表。实体类不是建表的唯一依据：生成列、联合索引和默认值常在 SQL 迁移里，排查时不能只看 Java 字段名。

## 20. 请求与数据字段的入门阅读手册

<a id="section-20-01"></a>

### 路径参数、查询参数和 JSON 参数怎么区分

`/venue/101` 中的 101 是路径参数；`/experience/cache?venueId=101` 中的 venueId 是查询参数；登录表单中的手机号与验证码则按 Controller 接收的请求体结构发送。Java 方法有几个参数，不等于这些参数都可以随意塞进 JSON。

在接口表找到路由之后，打开对应 Controller，检查 `@PathVariable`、`@RequestParam` 和 `@RequestBody`。复制参数名、大小写和 HTTP 方法。GET、POST、PUT 即使 URL 相同，也可能映射不同动作；浏览器地址栏只便于发送 GET，不能拿它代替 POST 登录或领取。

`?a=1&b=2` 在 Shell 里应把完整 URL 用引号包住，否则 `&` 会被解释成后台运行符。发送 JSON 时设置 Content-Type；发送 multipart 上传时使用对应格式，不能只把本地文件路径作为普通字符串当作文件上传。

<a id="section-20-02"></a>

### 从一份响应同时读出 HTTP 与业务结果

HTTP 状态表示请求处理层面，JSON success 表示当前业务动作。当前很多业务拒绝返回 HTTP 200 与 success=false；鉴权和限流可能使用 401、403、429。只看浏览器绿色网络条目会漏掉业务失败，只看 success 也会漏掉代理错误或非 JSON 响应。

读取顺序：先看 HTTP 状态与 Content-Type，再解析 JSON，检查 success，然后按接口定义读取 data。`Result` 的空字段会省略，不能强制要求失败响应一定有 data 或 total。表格分页与 Feed 游标分页结构不同，也不能按同一数组解析。

建议保存请求与响应模板时，用占位值替换个人凭证、手机号与真实敏感内容；保留字段结构、状态和对象 ID 关系即可。教学例子中的 UUID、数值和名称要明确是说明用值，实际链路必须使用自己的返回身份。

<a id="section-20-03"></a>

### 六种容易混淆的字段单位

| 字段或对象 | 单位或含义 | 常见误读 |
| --- | --- | --- |
| 券和订单的金额快照 | 分 | 1990 被展示成 1990 元 |
| 场馆 maxPrice 筛选 | 元 | 按金额分数传入造成范围过大 |
| minScore | 45 代表 4.5 分 | 输入 4.5 与整数约定不一致 |
| durationMicros | 微秒 | 与毫秒网络耗时直接相加 |
| occurredAt / bucket_ms | Epoch 毫秒 / 分钟起点毫秒 | 当成秒导致时间和窗口错位 |
| Redis TTL / PTTL | 秒 / 毫秒 | 把两个命令输出直接比较 |

金额统一先看字段说明再换算。时间统一先判断是否 Epoch、单位和时区再展示。ID 不是金额或时间，超过 JavaScript 安全整数的订单 ID 保留字符串，不做浮点运算。

<a id="section-20-04"></a>

### SQL 查询既要查 ID，也要查对象类型

Outbox 的 aggregate_id 由 kind 决定业务对象。教学读查询先带上 kind 和 ID，再观察 state、created_at 与时间字段；只按一个数字搜所有表可能恰好查到不相关对象。

数据库查询为空，需要看这张表在链路中何时出现。整点抢黄金时段入口刚受理时，订单表暂时没有记录可能合法；预约和 Stream 记录承担中间责任。订单事件历史暂时没有，也不必然表示订单没建立，它由后续消息投影产生。

当前表结构可从迁移和 Mapper 核对；先阅读表字典，再用数据库客户端查看实际列和索引。不要把一段演示 SELECT 得到的结果当作整个系统唯一事实，字段快照、执行状态和任务完成记录回答的是不同问题。

<a id="section-20-05"></a>

### 用数据库执行计划理解索引，而不是只数索引个数

在自己的开发库可以对只读语句使用 EXPLAIN，观察选择了哪个索引、预计检查行数和是否额外排序。下面语句只读演示表结构，具体执行计划依赖实际数据量与优化器选择，不承诺所有环境输出相同。

```sql
EXPLAIN
SELECT id, state, next_attempt_at
FROM tb_business_outbox
WHERE state = 'PENDING' AND next_attempt_at <= NOW()
ORDER BY id
LIMIT 20;
```

重点不是看到“用了索引”就结束，而是检查过滤条件、排序和返回数量如何影响扫描。唯一索引保证某种身份不重复，普通索引加速查询；一个查询更快不代表它能替代唯一约束维护并发正确性。

本演示使用简化条件，不等于真实领取 SQL。实际 Relay 还要处理过期 SENDING 租约、行锁与 SKIP LOCKED，阅读完整 Mapper 时再比较计划。OR 条件和加锁读取的行为应在具体数据库与负载下验证，不能仅凭简化 EXPLAIN 断言领取吞吐。

### 为一个接口建立最小验收卡片

```text
接口：HTTP 方法 + Java 路径
运行开关与身份：公开 / 本人 / 管理
输入来源：路径 / 查询 / JSON / multipart
关键字段单位：
本次接口成功的含义：
同步结束后一定存在的记录：
仍可能异步等待的任务：
可继续观察的原始 ID：
重复执行应得到的结果：
失败响应与恢复入口：
```

以体验浏览为例：POST 查询参数是 venueId；成功表示提交三条采集；返回 eventIds 便于后续查询；数据库记录不保证立即出现；再次 POST 会生成新事件而非重放。把这张卡填完整，就能避免“所有 success 都表示全部业务完成”的误解。

<a id="section-20-07"></a>

### 新手阅读 Mapper 的核对顺序

先看 namespace 是否对应 Java 接口；再看方法 ID、参数绑定和返回模型；随后看 WHERE 限制、排序、LIMIT、唯一约束和锁；最后找到调用它的 Service 事务。复杂语句一次只解释一个保证，别先改 SQL 尝试“优化”。

真正准备新增接口时，沿 DAO→Service→Controller 完成设计，保持显式 import、清晰方法命名和重点判断注释。完成后同步更新本附录的路径、参数、权限和状态说明，让使用者不用从实现代码猜接口契约。
